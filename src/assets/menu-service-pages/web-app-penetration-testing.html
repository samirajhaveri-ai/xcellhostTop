Definition

What is web application penetration testing?

It is a security exercise in which a qualified tester tries to gain access to your application in the same manner as an external attacker. We follow the OWASP Web Security Testing Guide and the PTES framework, check every result by hand and report what is exploitable, what is exposed and what should be fixed first.

An attacker’s point of view

We start where a stranger on the internet starts, then repeat the exercise as a logged-in user.

Verified by people

No finding reaches your report until an engineer has reproduced it manually.

Prioritised, not padded

Issues are ranked by real impact so your developers spend time where it counts.

What we test

Nine areas of security testing in web applications

We evaluate attack paths both before and after authentication to surface the vulnerabilities that put your users and data at risk.

01

Injection testing

SQL, NoSQL, command and template injection — any place untrusted input reaches an interpreter.

02

Authentication testing

Login, MFA, password reset and account lockout tested for bypass and brute-force weaknesses.

03

Authorisation testing

Whether one user can read or change another user’s data, or reach admin functions they should not.

04

Input validation testing

Cross-site scripting, file-upload abuse and unsafe redirects across every input the application accepts.

05

Configuration review

Default settings, verbose errors, exposed admin panels and missing security headers.

06

Session management testing

How sessions are created, stored, expired and protected against fixation or hijacking.

07

Encryption testing

TLS configuration, weak ciphers and sensitive data sent or stored without proper protection.

08

Business logic testing

Abuse of the workflow itself — skipped steps, price tampering, coupon reuse and race conditions.

09

Advanced technology testing

APIs, GraphQL, WebSockets, single-page apps, JWT handling and cloud-hosted components.

Testing modes

Black box, white box or grey box

We test from different vantage points depending on your threat model, the visibility you can share and what the release needs.

01
Zero knowledge

Black box testing

We test with no prior knowledge, exactly as an external attacker sees your application. Realistic, and a good measure of your exposed surface.

02
Full knowledge

White box testing

We test with source code and architecture access, usually before a major release, for the deepest coverage at code level.

03
Some knowledge

Grey box testing

We test with valid accounts and documentation, balancing realism with depth. This is our recommended default for most web applications.
