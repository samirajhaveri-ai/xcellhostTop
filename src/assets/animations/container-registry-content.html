Supply-chain security

Four gates between a push and production.

An image reaches your clusters only after it has been authenticated, scanned, signed and checked against your policy. Anything that fails a gate stays in the registry.

  1. Authenticate the push

    Pushes and pulls run over TLS with per-user or per-robot credentials. RBAC decides who can write to each repository.

  2. Scan every layer

    Images are scanned on push and on a schedule. Images pulled through from external registries are scanned automatically too.

  3. Sign and verify

    Content trust signs each image digest. Clusters verify the signature before running it, so tampered images never start.

  4. Admit by policy

    Set rules such as “block anything with a Critical or High CVE” or “only signed images in prod”. Detailed reports show exactly why.

Geo-replication & DR

Pull from the nearest copy. Survive a region outage.

Replicate repositories to more regions for lower-latency pulls and high availability. Add a fully replicated secondary region and your registry has a disaster-recovery copy ready.

  • Low-latency pulls — clusters pull from the replica closest to them.
  • Automatic sync — every push, tag and signature is copied to each replica region.
  • DR-ready — a secondary region holds a full copy, so pulls continue if the primary is unavailable.
  • Data stays in India unless you choose an overseas replica — useful for DPDP Act residency needs.

    Works with your tooling

    Standard commands. No new CLI.

    The registry speaks OCI, so docker, helm and kubectl work as they do today. The host below is illustrative — your project gets its own.

    bash
    # sign in with a robot account token
$ docker login registry.xcellhost.cloud -u robot-ci --password-stdin < token.txt
$ docker tag api:2.4.1 registry.xcellhost.cloud/<project>/api:2.4.1
$ docker push registry.xcellhost.cloud/<project>/api:2.4.1
2.4.1: digest: sha256:9c1e…4b7a  ·  scan queued
    bash
    # Helm 3.8+ stores charts as OCI artifacts
$ helm registry login registry.xcellhost.cloud -u robot-ci
$ helm package ./charts/payments
$ helm push payments-1.6.0.tgz oci://registry.xcellhost.cloud/<project>/charts
$ helm install payments oci://registry.xcellhost.cloud/<project>/charts/payments --version 1.6.0

    Use cases

    Where a private registry pays off.

    CI/CD acceleration

    Faster builds

    Cache base images and shared layers next to your CI runners, so builds stop re-downloading the same gigabytes.

    Multi-cluster

    Same image everywhere

    Dev, staging and prod pull the identical signed digest — what you tested is exactly what runs.

    Edge

    Images at remote sites

    Serve images to edge nodes in branches, plants or stores from the nearest replica, over thin links.

    Disaster recovery

    A registry that stays up

    Keep a full replica in a secondary region so deploys and restarts work through a regional outage.

    Hybrid cloud

    On-prem and cloud, one source

    Share images between on-premises clusters and XcellHost cloud clusters with the same credentials and policies.
