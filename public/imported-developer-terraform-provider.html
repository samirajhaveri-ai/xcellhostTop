      Overview

      Terraform lets you describe servers, networks, firewalls and load balancers in plain text files, then creates them for you — the same way every time. Because XcellCloud is built on OpenStack, you don't need a special plug-in: the official, open-source terraform-provider-openstack talks to XcellCloud's standard APIs (Keystone, Nova, Neutron, Cinder, Glance and Octavia) in the Mumbai region. You write .tf files, run terraform plan to see exactly what will change, and terraform apply to make it so. State can live in XcellHost's S3-compatible object storage, your pipeline can plan on every pull request, and an application credential keeps the access narrow. The provider and the APIs are free with your XcellCloud account — you pay only for what you build.

      Your exact endpoints are shown in the XcellCloud console → API Access. Endpoints, region and names on this page are examples.

      Provider setup

      Point the provider at XcellCloud — three ways to authenticate.

      All three use an application credential. Pick the one that fits where Terraform runs; the resources you write afterwards are identical.

      versions.tf
      terraform {
  required_version = ">= 1.6.3"

  required_providers {
    openstack = {
      source  = "terraform-provider-openstack/openstack"
      version = "~> 3.4"
    }
  }
}

  application_credential_secret = var.app_cred_secret

        State, modules & everyday commands
        Keep state safe, reuse modules, catch drift early.
        State maps your code to real resource IDs — and can contain sensitive values. Keep it in a private, versioned bucket, not on a laptop or in Git.
        
    
        
      
        backend.tf
        terraform {
  # EXAMPLE — S3-compatible remote state on XcellHost object storage.
  # Backend blocks cannot use variables; credentials come from
  # AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY (EC2-style credentials).
  backend "s3" {
    bucket = "acme-tfstate"
    key    = "web/prod/terraform.tfstate"
    region = "mumbai-1" # any string; region validation is skipped

    endpoints = {
      s3 = "https://s3.mumbai.xcellhost.cloud"
    }

    use_path_style              = true
    skip_credentials_validation = true
    skip_region_validation      = true
    skip_requesting_account_id  = true
    skip_metadata_api_check     = true
    skip_s3_checksum            = true

    # Terraform >= 1.10: S3-native lock file, where the endpoint
    # supports conditional writes — confirm before enabling.
    # use_lockfile = true
  }
}

        State checklist
        
        
          
          
        • Private bucket, versioning on, access only for the pipeline's EC2-style key.
          • 
          
        • One state file per environment (key = "web/prod/…"), so a dev apply can't touch prod.
          • 
          
        • Locking: S3-native lock files need conditional writes — confirm support with XcellHost; otherwise run applies from one pipeline only.
          • 
          
        • Commit .terraform.lock.hcl; never commit *.tfstate.

        CI/CD
        Plan on every pull request, apply on merge.
        Store the application credential and the state-bucket key as masked pipeline secrets. The pipeline formats, validates and plans; a human approves; the main branch applies.
        
    
        
      
        .github/workflows/terraform.yml
        # .github/workflows/terraform.yml
name: terraform
on:
  pull_request:
    paths: ["infra/**"]
  push:
    branches: [main]
    paths: ["infra/**"]

permissions:
  contents: read
  pull-requests: write

jobs:
  plan-apply:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: infra
    env:
      OS_AUTH_TYPE: v3applicationcredential
      OS_AUTH_URL: https://api.xcellhost.cloud:5000/v3
      OS_REGION_NAME: mumbai-1
      OS_APPLICATION_CREDENTIAL_ID: ${{ secrets.OS_APPLICATION_CREDENTIAL_ID }}
      OS_APPLICATION_CREDENTIAL_SECRET: ${{ secrets.OS_APPLICATION_CREDENTIAL_SECRET }}
      AWS_ACCESS_KEY_ID: ${{ secrets.STATE_ACCESS_KEY }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.STATE_SECRET_KEY }}
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.9.8
      - run: terraform fmt -check -recursive
      - run: terraform init -input=false
      - run: terraform validate
      - run: terraform plan -input=false -out=tfplan
      - if: github.ref == 'refs/heads/main' && github.event_name == 'push'
        run: terraform apply -input=false tfplan

        Security & India
        Least privilege by default — and your data stays in Mumbai.
        Infrastructure code holds the keys to your cloud. These are the habits we recommend to every XcellCloud customer.
        
    
        
      
        Least privilege
        Application credentials with only the member role (or reader for plan-only jobs), scoped to one project.
        
      
        Rotate keys
        Set an expiry, create the new credential, update the secret, then delete the old one.
        
      
        Never commit secrets
        .gitignore state, plans, *.tfvars and clouds.yaml; mark variables sensitive.
        
      
        MFA on the console
        People log in with MFA; pipelines use credentials. No shared admin passwords.
        
      
        IP allow-lists
        SSH and RDP rules limited to your office or VPN CIDR — reviewed in every pull request.
        
      
        Protect state
        State can hold IPs and secrets. Private, versioned bucket; least-privilege S3 keys.
        
      
        Data in India
        Resources in mumbai-1 stay in Indian data centres — helpful for DPDP Act obligations.
        
      
        Leaked a key?
        Delete the credential at once, check the project's activity, then issue a new one. Leak steps →
