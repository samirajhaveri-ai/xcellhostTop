Overview

XcellCloud Virtual Load Balancer is a managed load balancer in XcellHost's Mumbai cloud. Your users see a single IP and a single certificate; behind it, XcellHost spreads the work across as many instances as the day needs and quietly steps around any that fail. It accepts traffic on a public or private IP, terminates TLS if you want it to, and hands each request to a healthy backend — VMs, containers or Kubernetes nodes on your private network — using round robin, least connections or source-IP hash. It works at Layer 7 for websites and APIs (routing by host, path or header, cookie-based sticky sessions, HTTPS redirect) and at Layer 4 for TCP and UDP services. Health checks pull a failing server out of rotation and add it back when it recovers. XcellHost runs the platform 24×7 from Mumbai and bills it in rupees on one GST invoice.

How it works

Follow one request — from browser to backend.

Scroll to walk a request through the load balancer. The diagram rebuilds itself at each step.

  1. 01
    Resolve to one address

    Your domain points at the load balancer's floating IP. Users never see — or depend on — an individual server.

  2. 02
    Listener accepts & decrypts

    An HTTPS listener completes the TLS 1.2 or 1.3 handshake with your certificate and redirects plain HTTP to HTTPS.

  3. 03
    Rules pick a pool

    Layer-7 rules read host, path or headers — /api to the API pool, /shop to the store, the rest to web.

  4. 04
    An algorithm picks a server

    Within the pool, least connections sends the request to the backend with the fewest open connections.

  5. 05
    Health checks guard the pool

    A backend that fails its probes is drained and skipped; traffic flows to the rest until it passes again.

  6. 06
    Scale out, watch, repeat

    Auto-scaling adds instances that join the pool automatically; logs and metrics stream to your dashboards.

Two load balancers

Application or Network — pick by what you are carrying.

Both are managed, both run in Mumbai, both are priced the same. The difference is how deep into the traffic they look.

Reads every HTTP request, then decides.

The Application load balancer terminates HTTPS, inspects the request and routes it by rule. It is the right choice for websites, REST and GraphQL APIs, microservices and container platforms.

  • Host, path and header routing — api.example.in, /shop/*, X-Tenant
  • TLS 1.2 / 1.3 termination with HTTP → HTTPS redirect
  • Cookie-based sticky sessions for carts and logins
  • WebSocket and HTTP/2 from browsers
  • Containers & Kubernetes — front an ingress or node pool

Moves connections fast, without opening them.

The Network load balancer works on TCP and UDP connections. It does not read the payload, so it suits databases, remote desktops, VoIP, MQTT, game servers and anything that must keep end-to-end TLS.

  • TCP and UDP listeners on any port
  • Static public IPv4 to whitelist with partners and banks
  • TLS passthrough or offload — your choice per listener
  • High throughput, low overhead for long-lived connections
  • RDP farms — Tally and ERP users spread across session hosts

    Round robin, least connections and source-IP hash, the three standard methods. Round robin suits identical servers with even requests; least connections adapts when some requests take longer; source-IP hash keeps each client on the same server. Weighted variants can be set up on request.

After a set number of failed probes the backend is taken out of rotation; after a set number of good probes it is brought back. The health-check visualiser on this page shows the timing.
