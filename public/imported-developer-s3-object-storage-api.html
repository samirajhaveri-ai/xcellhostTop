    Three settings, every tool

    Endpoint https://s3.mumbai.xcellhost.cloud — always HTTPS. Region mumbai-1 — used inside the SigV4 signature, so it must match. Addressing path-style (/bucket/key) works everywhere; virtual-hosted needs wildcard DNS.

    Set keys through a profile, XH_ACCESS_KEY/XH_SECRET_KEY environment variables or your CI's secret store. Recent AWS SDKs add CRC checksums by default; if an upload is rejected with a checksum error, set the checksum options to when_required as shown.

    • TLS on every request; plain HTTP is not offered
    • Objects stored in the Mumbai region
    • Rotate keys on a schedule — the console keeps two active while you switch

    The S3 API features you'll use most

    Buckets & objects

    Create buckets, then PUT, GET, HEAD, COPY and DELETE objects by key. Prefixes like 2026/10/ act as folders.

    Multipart upload

    Split big files into parts, upload them in parallel, retry only the part that failed, then complete into one object.

    Presigned URLs

    Hand out a time-limited link to download or upload one object — no keys shared, expires on its own.

    Versioning

    Keep every version of an object. An overwrite or delete becomes recoverable instead of final.

    Lifecycle rules

    Expire temp files, prune old versions and abort stuck multipart uploads automatically by prefix and age.

    Object Lock (where enabled)

    Write-once retention in governance or compliance mode — useful for audit logs and ransomware-safe backups.

    CORS

    Let a browser app on your domain upload straight to a bucket with a presigned PUT — no proxy server.

    Bucket policies

    JSON policies allow or deny actions per bucket and prefix — e.g. public read on public/* only.

    How requests are addressed and signed

    Path-style vs virtual-hosted — and what SigV4 actually signs.

    Every S3 request names a bucket and is signed with your secret key. Here is where the bucket goes in the URL, and the five steps your SDK runs to sign it.

    Path-style works everywhere

    https://s3.mumbai.xcellhost.cloud/acme-invoices/2026/10/invoice-0425.pdf

    The bucket is the first path segment. One hostname and one TLS certificate cover every bucket — the safest default for S3-compatible endpoints. Set addressing_style = path, forcePathStyle: true or force_path_style = true.

    Virtual-hosted where offered

    https://acme-invoices.s3.mumbai.xcellhost.cloud/2026/10/invoice-0425.pdf

    The bucket becomes a sub-domain. It needs wildcard DNS and a wildcard certificate on the endpoint, and bucket names with dots break TLS. Use it only if your console lists a virtual-hosted endpoint.

    1Canonical request

    Method, path, sorted query, signed headers and the payload hash, joined by newlines.

    GET\n/acme-invoices/…\nhost;x-amz-date
    2String to sign

    Algorithm, timestamp, credential scope and the SHA-256 of step 1.

    AWS4-HMAC-SHA256\n20261015/mumbai-1/s3/aws4_request
    3Signing key

    Your secret key is HMAC'd with date, region, service and "aws4_request".

    kDate → kRegion → kService → kSigning
    4Signature

    HMAC-SHA256 of the string to sign with the signing key, as 64 hex characters.

    X-Amz-Signature=<64 hex>
    5Server verifies

    XcellCloud repeats the steps with its copy of the key. Clock skew over ~15 minutes fails.

    200 OK · or 403 SignatureDoesNotMatch

    Your secret key never travels — only the signature does. A 403 SignatureDoesNotMatch usually means a wrong region (must be mumbai-1), a wrong addressing style, or a proxy rewriting headers. RequestTimeTooSkewed means the client clock is off — sync it with NTP.

      When to go multipart

      The high-level commands (aws s3 cp, upload_file, rclone copy, mc cp) switch to multipart automatically above a threshold. Tune part size and concurrency for big files on fast links.

      • Above ~100 MB, multipart is faster and more resilient
      • A failed part is retried alone — not the whole file
      • Abandoned uploads still use space: add an AbortIncompleteMultipartUpload lifecycle rule
      • More parallel parts help until your uplink is full

      Security & India

      Keys are passwords — treat them that way.

      Most object-storage leaks come from a key pasted into code or a bucket left public. These habits prevent both, and keep your data where Indian regulation expects it.

      One key per app

      Separate keys for the website, the backup job and CI. Revoke one without touching the rest.

      Rotate on a schedule

      Create the new key, deploy it, then delete the old one — every 90 days or when someone leaves.

      Never commit secrets

      Add .env, .s3cfg and rclone.conf to .gitignore; use CI secret stores.

      Private by default

      Keep buckets private and share with presigned links. Make a single prefix public only on purpose.

      MFA on the console

      The account that creates keys deserves a second factor. Restrict console access by IP where you can.

      DPDP Act 2023

      Personal data in the Mumbai region, encrypted in transit, with versioning and lifecycle to honour retention and erasure.
