Overview

A dead detection looks exactly like a quiet week.

Security tools fail loudly when they crash. Detection content fails silently. A query keeps running against a field that was renamed. An agent is removed from a server and nobody notices. A noisy rule is tuned and, along with the noise, stops catching the real thing. The dashboard stays green.

XcellHost Breach & Attack Simulation (BAS) re-runs known attacker behaviour — safely, in agreed windows, under written rules of engagement — and checks the result against your real monitoring. The first run is a baseline. Every run after it shows what improved and what quietly broke, mapped to MITRE ATT&CK tactics.

Why re-running is needed

Four ways detection breaks without anyone being told.

Detection content is the one part of a security estate that can fail completely and still look healthy.

user_nameaccount
01

Schema & product change

A vendor renames a field or retires a table. The query still runs — and returns nothing.

02

Tuning that went too far

The most common cause. A noisy rule is quietened and the true positives go with the noise.

03

Sources that stopped arriving

A connector fails, an agent is removed, a licence changes. Coverage disappears with no alert.

04

Estate drift

New servers, SaaS apps and identities arrive. Rules written for last year's estate don't see them.

How it runs

Baseline, repeat, compare, fix — and the fix is part of the service.

Cycle 06monthly · sample
  1. 01
    Agree the scope

    Behaviours, target hosts and accounts, run windows, exclusions and stop conditions — written down and signed before anything runs.

  2. 02
    Baseline it

    The first run records what is detected, what is noisy and what is invisible today. It is useful on its own.

  3. 03
    Close the gaps

    Missed behaviours get new detections, written and backtested against your history. Noisy ones get tuned. Included in the service.

  4. 04
    Repeat on a cycle

    Monthly or quarterly, depending on how fast your estate changes — and after any migration, platform change or acquisition.

  5. 05
    Report the movement

    Improvements and regressions since the last run, by ATT&CK tactic, with time-to-alert and time-to-ticket for each behaviour.
