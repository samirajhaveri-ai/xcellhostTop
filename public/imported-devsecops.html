Overview

Shift left to catch it early. Shift everywhere to keep it caught.

Most security problems are cheapest to fix in the editor and most expensive in production. Shift-left moves checks to where code is written: the pull request, the dependency update, the Terraform plan. But a clean build can still be tampered with, misconfigured at deploy or attacked at runtime — so shift-everywhere adds controls to the build system, the artifact, the cluster and the running workload.

XcellHost DevSecOps runs both as a service. We wire the scanners into GitLab™, GitHub™, Jenkins™ or Azure DevOps™, tune the rules so developers are not buried in noise, generate an SBOM for every release, sign artifacts and enforce the result in Kubernetes. Our application-security engineers triage findings and our 24×7 SOC in Mumbai watches what runs.

Software supply chain

Know what is inside. Prove where it came from.

Software supply-chain failures sit at number three in the OWASP Top 10:2025. Three controls answer the questions a customer, auditor or regulator will ask.

01 · SBOM

What is inside?

An SBOM lists every component, version, supplier, licence and hash in a release. We generate one per build and keep it beside the artifact.

CycloneDXOWASP standard, also ECMA-424SPDXLinux Foundation, ISO/IEC 5962:2021
  • Search all releases for one vulnerable package
  • Share with customers and auditors on request
  • Fields aligned to CERT-In's SBOM guidelines
02 · SLSA build levels

How was it built?

SLSA (version 1.2, November 2025) grades build integrity. Most teams start at L0; our managed runners take you to L2, and hardened, isolated builds to L3.

  1. L0No guarantees
  2. L1Provenance exists
  3. L2Hosted build, signed provenance
  4. L3Hardened, isolated builds
Build track levels from the SLSA specification. Version 1.2 also adds a Source track.

            India regulations

            SBOMs and secure SDLC are now asked for by Indian regulators.

            DevSecOps does not make you compliant by itself. It produces the SBOMs, scan records and change evidence these rules expect.

            CERT-InTechnical Guidelines on SBOM

            Version 1.0 issued 3 October 2024; version 2.0 on 9 July 2025 extended it to cryptographic (CBOM), AI (AIBOM), hardware (HBOM) and quantum (QBOM) bills of materials. Aimed at government, essential-services and software-export organisations, and their suppliers.

            SEBICSCRF, 20 August 2024

            The Cybersecurity and Cyber Resilience Framework asks regulated entities to obtain and maintain SBOMs for critical systems and new core software, updated with every software change, and to cover supply-chain risk in contracts.

            RBIIT Governance Master Direction

            RBI's Master Direction on IT Governance, Risk, Controls and Assurance Practices (7 November 2023, in force from 1 April 2024) expects security across the software development life cycle and vendor risk management. RBI advisories have also pointed regulated entities to CERT-In's SBOM guidelines.

            6 hCERT-In incident reporting

            CERT-In's April 2022 directions require reportable incidents — including compromise of software supply chains — to be reported within 6 hours of noticing them. Runtime detection and signed-artifact records shorten that investigation.

            Regulatory summaries checked November 2026 from CERT-In, SEBI and RBI publications and law-firm and audit-firm summaries (Khaitan & Co, July 2025; KPMG India, December 2025). For orientation only — not legal advice. Confirm current requirements with the regulator.

              FAQ

              DevSecOps, answered.

              DevSecOps builds security into every stage of software delivery — planning, code, build, test, release, deploy and run — instead of testing once at the end. Developers, operations and security share the same pipeline, the same findings and the same metrics.

              Shift-left moves checks earlier, to the pull request and build, where fixes are cheapest. Shift-everywhere keeps controls at later stages too — signing, admission policy and runtime detection — because a clean build can still be tampered with or misconfigured after it leaves CI.

              Fast checks such as secrets and incremental SAST run on the pull request; slower ones such as DAST run on a schedule or on staging. We tune rules and triage findings before developers see them, and we track DORA lead time and deployment frequency so any slowdown is visible.

              No. We integrate with GitLab™, GitHub™, Azure DevOps™, Jenkins™ and Bitbucket™. If you want us to run the platform as well, see our GitLab and GitHub services pages.

              A software bill of materials lists every component in a release with its version, supplier, licence and hash. We produce CycloneDX or SPDX, both of which CERT-In's guidelines accept, and keep one SBOM per release beside the artifact.

              It produces the evidence those rules ask for — SBOMs, scan records, signed artifacts and change history — and maps it in the monthly report. Compliance remains your organisation's responsibility; confirm current requirements with the regulator.

              SLSA grades build integrity from L0 (no guarantees) to L3 (hardened, isolated builds with protected provenance signing). Supply-Chain Secure uses hosted runners with signed provenance, which is the L2 pattern; Enterprise adds the hardened L3 build platform.

              Scanners and build runners run in your environment or in isolated runners in our Mumbai Tier IV data centre, so source code stays in India. We do not use your code to train models.
