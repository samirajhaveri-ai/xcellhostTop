    What a kubeconfig holds

    A cluster (API server URL + CA certificate), a user (token, client certificate or an OIDC login command) and a context that pairs them with a default namespace. kubectl reads $KUBECONFIG or ~/.kube/config.

    • Treat it like a password — chmod 600, never commit it
    • People sign in with OIDC; pipelines use ServiceAccount tokens
    • Prefer short-lived tokens (--duration=1h) over long-lived secrets
    • Check what you can do with kubectl auth can-i --list

    Add -v=6 to any kubectl command to see the exact REST requests it sends — the translator below explains them.

    Kubernetes API concepts you'll use daily

    Resources & verbs

    Pods, Deployments, Services and more, each a REST resource you get, list, watch, create, patch or delete.

    API groups & versions

    Core objects live under /api/v1; the rest under /apis/<group>/<version> — e.g. apps/v1.

    Namespaces

    Folders for resources and the natural boundary for RBAC, quotas and network policies — one per team or app.

    RBAC

    Roles list allowed verbs on resources; RoleBindings grant them to users, groups or ServiceAccounts.

    ServiceAccounts

    Identities for workloads and pipelines, with short-lived, audience-bound tokens instead of shared passwords.

    Watch

    ?watch=true streams changes as they happen — how controllers, Argo CD and kubectl get -w stay current.

    Server-side apply

    The API server merges your YAML and tracks which tool owns each field — fewer conflicts between kubectl, Helm and GitOps.

    CRDs & operators

    Custom resources extend the API — cert-manager, Argo CD and database operators all add their own kinds.

    Integrations

    Load balancers, volumes, policies, Helm and GitOps — the YAML you'll need.

    On OpenStack-based clouds like XcellCloud, clusters typically run the OpenStack cloud-controller-manager (load balancers through Octavia) and the Cinder CSI driver (block volumes). Confirm which integrations are enabled on your cluster.

    Service type: LoadBalancer→cloud-controller-manager→Octavia LB + public IP

    Create a Service of type LoadBalancer and the OpenStack cloud-controller-manager asks Octavia for a load balancer; the external IP appears in kubectl get svc. Annotations tune it — typical OpenStack integration; confirm on your cluster.

    apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: shop
  annotations:
    # keep the floating IP if the Service is deleted (OpenStack CCM)
    loadbalancer.openstack.org/keep-floatingip: "true"
    # internal-only load balancer instead of a public IP:
    # service.beta.kubernetes.io/openstack-internal-load-balancer: "true"
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - name: http
    port: 80
    targetPort: 8080
    kubectl apply -f service.yaml
kubectl get svc web -n shop -w          # EXTERNAL-IP goes from <pending> to an address
kubectl describe svc web -n shop        # events from the cloud-controller-manager
    PersistentVolumeClaim→cinder.csi.openstack.org→Cinder volume, attached to the node

    A StorageClass with the Cinder CSI provisioner turns every claim into a block volume in XcellCloud. WaitForFirstConsumer creates the volume in the same zone as the pod. The volume type name below is a placeholder.

    apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: cinder-ssd
provisioner: cinder.csi.openstack.org
parameters:
  type: ssd                       # Cinder volume type — placeholder
allowVolumeExpansion: true
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

    Start each namespace with a default-deny policy, then allow only the traffic each app needs. Network policies need a CNI that enforces them (for example Calico or Cilium) — confirm on your cluster.

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-from-ingress
  namespace: shop
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes: ["Ingress"]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress

    Git repo→Argo CD (in-cluster)→Kubernetes API

    With GitOps, an agent inside the cluster pulls the desired state from Git and applies it — no cluster credentials in your CI system. This Argo CD Application syncs one folder and heals drift.

  name: shop
  namespace: argocd

  project: default

    Security & India

    The API server is the front door — lock it properly.

    Whoever can call the Kubernetes API can run code in your cluster. These defaults keep that list short and auditable.

    OIDC + MFA for people

    Sign in through your identity provider; removing a leaver there ends their cluster access.

    Short-lived tokens

    Use kubectl create token --duration or projected tokens, not long-lived Secret tokens.

    Least-privilege RBAC

    Namespace Roles, no wildcards, and cluster-admin kept for break-glass only.

    No kubeconfigs in Git

    Add kubeconfig files to .gitignore; give CI a scoped ServiceAccount through its secret store.

    Restrict API access

    Allow the API server only from office, VPN and CI IP ranges where the cluster supports it.

    DPDP Act 2023

    Personal data in Mumbai-region volumes, encrypted Secrets at rest, and audit logs that show who accessed what.
